# FraudLens

Fraud detection on a heavily imbalanced public card-transaction dataset, evaluated honestly:
a time-based split, PR-AUC and recall at fixed precision with bootstrap confidence intervals,
a decision threshold chosen from an explicit cost model, per-transaction explanations, and a
tested FastAPI scoring service.

Rebuilds the design of a Fall 2024 course project (CSC 450, Berea College) whose original code
was not preserved. Requirements: [docs/prd/FL-01-fraudlens.md](docs/prd/FL-01-fraudlens.md).

## 1. What it does, and why accuracy is the wrong metric

FraudLens trains four models to flag fraudulent card transactions: a logistic-regression
baseline, a random forest, histogram gradient boosting and an isolation forest (an
unsupervised anomaly detector trained on legitimate transactions only). It chooses one model
and an alert threshold using validation data only, reports it once on a held-out final slice of
time, and serves it behind an API that explains every score.

About 0.17% of transactions in this dataset are fraud. A "model" that answers *legitimate*
every time is therefore right more than 99.8% of the time and catches nothing. Accuracy is
reported below only to show that. The project uses metrics that count what matters for rare
events: precision-recall AUC, the recall you get when 90% of alerts must be real fraud, the
precision you get when 80% of fraud must be caught, and the money that a threshold saves or
loses.

## 2. The dataset, its license and its limits

The [ULB Credit Card Fraud Detection dataset](https://www.kaggle.com/datasets/mlg-ulb/creditcardfraud):
284,807 transactions by European cardholders over two days in September 2013, 492 of them
fraud. It is published under the Open Database License (ODbL 1.0). The file is never
committed. [data/README.md](data/README.md) explains how to get it and records its SHA-256.

Limits that shape every result here:

- **PCA features.** `V1`–`V28` are anonymised principal components. Explanations can say
  "V14 pushed this score up" but not what V14 *is*.
- **Two days, 2013, one issuer.** Fraud changes quickly. Nothing here predicts performance on
  another portfolio, another year or in production.
- **Few frauds per slice.** The time split leaves only a few dozen frauds in the validation and
  test slices, so every interval is wide.

## 3. How it is evaluated

| Step | What happens |
|---|---|
| **Time split** (EV-1) | Sort by `Time`; first 60% train, next 20% validation, last 20% test. Cuts move to the next distinct timestamp so no second straddles two slices. Random splits are not used for headline numbers because they leak future patterns into training. |
| **Leakage control** (EV-6) | Feature scaling and any resampling live inside a scikit-learn/imbalanced-learn `Pipeline` fitted on training rows only. Tests check that scaler statistics equal training-row statistics, that samplers never see validation or test rows, and that corrupting every test row changes nothing in the trained model. |
| **Model search** (FR-8) | Randomised search with a fixed seed and a small budget per model (`config.yaml`). Each setting is trained on train and scored by validation PR-AUC. |
| **Imbalance** (EV-5) | Class weights, random undersampling and SMOTE compared for every supervised model, resampling inside the training fit only. |
| **Selection and calibration** (FR-9) | Highest validation PR-AUC wins; its probabilities are calibrated (sigmoid) on validation. |
| **Cost model** (EV-7) | A missed fraud costs its amount; every alert costs a $5 review. The threshold that minimises total cost on validation is applied unchanged to test and compared with "flag nothing" and "flag everything". |
| **Test, once** (EV-2 to EV-4) | Only `fraudlens.evaluate` reads test rows, after every choice is fixed. Metrics get 95% percentile bootstrap intervals (1,000 resamples). Model differences use a *paired* bootstrap and are only called significant when the interval excludes zero. |

Why not accuracy: predicting "legitimate" for every test transaction scores **99.87% accuracy** and catches none of the 75 frauds. The served model scores 99.95% and catches 55. Accuracy separates them by 0.08 percentage points, so it is reported only to make this point, never to compare models.

ROC-AUC is reported for completeness only. With so few frauds, the false-positive rate's denominator is huge, so ROC-AUC stays high even for a model that is of little use: `isolation_forest` reaches ROC-AUC 0.957 but PR-AUC only 0.078.

## 5. Explainability

- **Global:** permutation importance on the validation slice, measured as the drop in PR-AUC
  when a column is shuffled ([plot](reports/feature_importance.png),
  [table](reports/feature_importance.csv)).
- **Per transaction:** `/score` returns the five inputs that moved this transaction's score the
  most. Each input is replaced with its training median and the transaction is re-scored; the
  contribution is the change in fraud probability, positive when the feature pushed towards
  fraud. All 30 substitutions are scored in one batch.

What PCA features can tell you: which components carry the signal (V14 dominates), and how far
a transaction's components sit from typical values. What they cannot tell you: anything a fraud
analyst could act on directly, such as merchant, location or device. `Time` reaches the model
only as hour of day, and `Amount` as log1p(Amount).

## 6. The API

```bash
# Train (about 8 minutes on a laptop), then serve the model named in artifacts/LATEST
uv run python -m fraudlens
docker compose up --build          # http://localhost:8000/docs
```

The image runs as a non-root user with a read-only filesystem and loads one versioned artifact
from the read-only `./artifacts` mount at startup. It never trains.

| Endpoint | Purpose |
|---|---|
| `POST /score` | Fraud probability, `flag`/`allow` at the cost-chosen threshold, model version, top 5 contributing features |
| `GET /health` | Liveness and the loaded version |
| `GET /model` | Model name, version, training date, test PR-AUC with CI, threshold, data hash, code version |

An illustrative transaction (hand-made, not a row from the dataset) is in
[scripts/example_transaction.json](scripts/example_transaction.json):

```bash
curl -s localhost:8000/score -H 'content-type: application/json' \
  -d @scripts/example_transaction.json
```

Validation is strict: a missing feature, a string where a number belongs, `NaN`, an unknown

values. Each request is logged as one JSON line with request id, path, status, latency,
decision and model version, and never feature values.

## 7. Limitations and next steps

- **This is not a production system.** The numbers describe one public 2013 dataset.
- **Concept drift.** Fraudsters adapt. A real deployment needs drift monitoring on inputs and
  scores, and scheduled retraining checked against a fresh time slice.
- **Label delay.** Here every label is known immediately. In practice chargebacks arrive
  weeks later and some fraud is never reported, so recent training data is incomplete and
  evaluation lags behind.
- **Small validation slice.** Model choice, calibration and threshold all rest on a few dozen
  validation frauds, which makes model selection noisy (see the results above).
- **One global threshold.** Because a missed fraud costs its amount, a rule that flags when
  *probability × amount* exceeds the review cost would probably save more. It is a natural
  next step.
- **What a production version would add:** monitoring and alerting, a feedback loop from
  human reviewers, champion/challenger evaluation, a feature store with real (non-PCA)
  features, and model governance (approval, rollback, audit of every decision).

## Development

```bash
uv sync                                      # Python 3.12, exact pins from uv.lock
uv run ruff check . && uv run ruff format --check .
uv run mypy fraudlens service
uv run pytest --cov=fraudlens --cov=service  # synthetic fixture only; fails under 85%
uv run python -m fraudlens                   # train + evaluate + report (needs the dataset)
uv run python -m fraudlens.report            # rebuild the README results from reports/
uv run python scripts/load_test.py           # 1,000-request latency run against a live API
```

CI ([.github/workflows/ci.yml](.github/workflows/ci.yml)) runs lint, types and tests with
coverage on every push, using the synthetic fixture only. A manual `workflow_dispatch` run
with `full_evaluation` downloads the dataset, checks its hash and runs the full evaluation.

```
fraudlens/   data, features, models, costs, explain, train, evaluate, report, plots, artifacts
service/     FastAPI app, pydantic schemas, Dockerfile
tests/       unit, leakage, pipeline and service tests; synthetic fixture
reports/     generated metrics, curves and report.md (committed)
config.yaml  seed, split, costs, search budgets
```
